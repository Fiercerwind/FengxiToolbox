# OCR 多后端实现路径调研

日期：2026-04-20

## 目标
- 不把风兮工具箱的 OCR 设计绑定到单一家实现路径。
- 保持产品层面的风兮自有工作流，同时在技术层面兼容多种 OCR 后端。
- 当一种后端在某类扫描件、语言或版式上效果不理想时，允许快速切换。

## 当前采纳的架构方向
- 公共层：
  - PDF 页面提取与双层可搜索 PDF 生成统一由 `tools/fx_pdf_ocr.py` 负责。
  - 页面渲染、透明文字层叠加、原生文本保留、密码处理、工作流日志均与具体后端解耦。
- 可切换后端：
  - `rapidocr`
  - `paddleocr`
  - `easyocr`
  - `tesseract_cli`
  - `auto` 自动选择

## 各路径定位

### 1. RapidOCR
- 定位：
  - 当前默认优先后端。
  - 轻量、启动快、Windows 本地分发相对友好。
- 适合：
  - 风兮工具箱默认桌面体验。
  - 希望减少整套依赖、保持较好速度与较低接入复杂度的场景。
- 风险：
  - 本质上是对 OCR 模型与推理框架的工程封装，不应让产品设计只围绕它一条路展开。

### 2. PaddleOCR
- 定位：
  - 官方路线后端。
  - 模型、版面和文档能力更全，适合做“高能力但较重”的可选方案。
- 适合：
  - 追求更完整官方生态。
  - 后续若扩展表格、版面分析、文档结构化，可优先研究这一条。
- 风险：
  - 依赖重，Windows 打包与环境管理成本更高。

### 3. EasyOCR
- 定位：
  - Torch 路线的补充型后端。
  - 语言覆盖广，适合作为某些特殊语言或效果兜底。
- 适合：
  - 非中文主场景。
  - 用户主动安装后作为备选。
- 风险：
  - 体积大，模型下载与 Torch 依赖会增加首次使用成本。

### 4. Tesseract CLI
- 定位：
  - 外部命令行后端。
  - 老牌成熟，系统边界清晰，适合作为“独立于 Python OCR 包”的备用通道。
- 适合：
  - 用户本机已安装 Tesseract。
  - 需要明确外部依赖、方便排障的环境。
- 风险：
  - 中文与复杂版面的综合表现通常不应作为风兮默认路线。

## 风兮当前实现约定
- 对外展示：
  - 始终以“风兮工具箱 OCR 工作流”对外呈现。
  - 不在产品层文案上绑定任意一家第三方成品软件。
- 对内实现：
  - 允许并鼓励多后端并存。
  - 新增 OCR 能力时优先复用公共 PDF 工作流，不重复造轮子。
- 自动选择顺序：
  - `rapidocr -> paddleocr -> easyocr -> tesseract_cli`
- 切换原则：
  - 默认 `auto`
  - 识别效果不理想时允许用户手动切换到指定后端

## 后续可继续演进
- 基于后端能力做“效果优先 / 速度优先”预设。
- 增加多页抽样预览，先对首页试 OCR 再批量跑。
- 对不同后端记录成功率与耗时，后续可做风兮自己的经验排序。
- 未来如加入 OCRmyPDF，应将其视为 PDF 工作流方案，而不是唯一 OCR 引擎。
